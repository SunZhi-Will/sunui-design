# SunUI Admin 統計系統規劃

> 撰寫日期：2026-11-13。依據：repo 現況（`apps/web/lib/license.ts`、`lib/installs.ts`、`middleware.ts`、`app/api/*`、`app/r/pro/[name]/route.ts`、`app/mcp/route.ts`）、`LAUNCH.md`、`reports/商業模式深度分析-2026-11-06.md`，以及當日查詢的 Polar、Upstash、Vercel、PostHog、Neon 官方文件。【已驗證】表示讀過一手文件，【二手】表示來自第三方整理，【建議】是本報告的判斷。

## 一句話結論

**不要重做 Polar 已經有的報表，admin 要做的是 Polar 看不到的東西：「買了授權的人有沒有真的在用」與「AI 通路帶來多少需求」。** 訂單、營收、結帳轉換率直接向 Polar 的 Metrics API 拿；授權使用率、Pro 區塊安裝、未授權的 Pro 嘗試（401）、MCP 搜尋與零結果查詢，這些只有 SunUI 自己的伺服器知道，也是決定 2027-01-11「Founding 50 筆」門檻前後要怎麼調整的關鍵資料。

第一階段只用現有的 Upstash Redis，不加資料庫、不加套件，目標在 **2026-11-27 Founding 開賣前** 上線。

## 1. 現況盤點：已經有什麼、缺什麼

| 資料 | 現況 | 問題 |
|---|---|---|
| 免費安裝 | `middleware.ts` 攔 `/r/<name>.json`，寫進 Redis 每日 hash，保留 180 天；`/api/installs` 用 Bearer token 讀 JSON | 只能 curl 看，沒有畫面；沒有依系列（commerce / motion / story）分組 |
| Pro 授權驗證 | `lib/license.ts` 呼叫 Polar validate，快取、限流、IP 計數都在 **單一 instance 記憶體** | Vercel serverless 有多個 instance，限流與「同一把 key 一天超過 20 個 IP」的分享偵測實際上不可靠；**沒有任何 Pro 安裝紀錄** |
| 退款撤銷 | `invalidateLicense()` 註解寫「由 Polar webhook 呼叫」 | **webhook route 還不存在**；就算存在，也只清得到收到請求那個 instance 的記憶體 |
| 401（沒 key 想裝 Pro） | 直接回訊息 | 沒記錄。這是最直接的購買意圖訊號，目前完全流失 |
| MCP 伺服器 | 6 個工具（search_blocks、get_block、plan_install、get_design_rules、search_icons、get_icon） | 沒有任何呼叫紀錄，看不到 agent 在找什麼、找不到什麼 |
| 訂單與營收 | 只在 Polar 後台 | 無法和授權使用、安裝資料對照 |
| Waitlist | Resend contacts | 人數只能去 Resend 看 |
| 網站流量 | 無 | pricing 頁瀏覽、結帳按鈕點擊都沒有 |

結論：要做 admin，先要補「資料收集」，畫面反而是最簡單的部分。

## 2. 外部工具能給什麼（查詢結果）

### Polar 已經提供的
- **Metrics API**：`GET /v1/metrics/`，參數 `start_date`、`end_date`、`interval`（year / month / week / day / hour）、`timezone`、`product_id`、`billing_type`，可只要指定的 `metrics`。回傳中與 SunUI 有關的有 `orders`、`revenue`、`net_revenue`、`cumulative_revenue`、`average_order_value`、`one_time_products`、`one_time_products_revenue`、`checkouts`、`succeeded_checkouts`、`checkouts_conversion`。金額單位是 cents，需要 `metrics:read` scope【已驗證】。
- **Orders API** 可列出訂單，另有 CSV 匯出【二手，需實測】。
- **License Keys API**：`GET /v1/license-keys/` 列出組織所有 key（每頁最多 100），單把 key 的回應含 activations；scope 為 `license_keys:read`，用 organization access token（`polar_oat_` 開頭）【已驗證端點，token 前綴為二手】。
- **Webhooks**：`order.created / updated / paid / refunded`、`refund.created / updated`、`benefit_grant.created / updated / revoked`、`checkout.created / updated / expired`、`customer.*`。**沒有專屬的 license key 事件**，授權發放與撤銷要看 `benefit_grant.*`【已驗證】。

所以「訂單數、營收、客單價、結帳轉換率」不需要自己算，直接打 Metrics API 並快取即可。

### 網站流量工具
| 工具 | 免費額度 | 對 SunUI 的問題 |
|---|---|---|
| Vercel Web Analytics | Hobby 每月 50,000 事件，**不含 custom events**，報表只保留 1 個月，超量暫停收集【已驗證】 | 量不到「點了結帳」，保留期太短，撐不過 2027-01 複審 |
| PostHog | 每月 100 萬事件、5,000 段 session replay【已驗證事件額度，replay 為二手】 | 功能最全，但要放 JS、cookie 同意、隱私頁要改 |
| Plausible | 雲端約 US$9 起，無免費層【二手】 | 只有頁面瀏覽 |
| Umami Cloud | Hobby US$0，10 萬事件、1 個網站、保留 6 個月【二手】 | 可行的輕量選項 |

【建議】漏斗中最重要的兩步（看 pricing、點結帳）用 **伺服器端計數** 就能拿到（見 4.4），不必放追蹤 JS。頁面流量真的需要時再加 Umami Cloud 或 PostHog，不列入第一階段。

### 儲存
- **Upstash Redis（已在用）**：免費 500K commands / 月、256 MB；加付款方式後改隨用隨付，每 10 萬 commands US$0.20【已驗證】。
- **Neon Postgres**：免費層不會因閒置暫停，適合之後需要 SQL 交叉查詢時再上；Supabase 免費專案閒置會被暫停【二手】。

## 3. 指標設計：看什麼、為什麼

業界給早期獨立產品的共識是「一頁、5 到 7 個數字、每週看一次」，不要照抄大公司儀表板【二手】。SunUI 是買斷制，MRR、churn 這類訂閱指標不適用，改用下列指標。

### 3.1 北極星與決策門檻（總覽頁最上方）

| 指標 | 定義 | 為什麼 | 門檻（來自商業模式分析） |
|---|---|---|---|
| Founding 付費筆數 / 剩餘席次 | `orders` 中 Founding 產品，扣掉已退款；席次上限 150 | 直接對應 2027-01-11 門檻 | 50 筆，未達則檔期定位退回「通用轉換區塊」 |
| 淨營收（累計、本週） | Polar `net_revenue` | 實際入帳 | 無 |
| **授權啟用率** | 至少裝過 1 個 Pro block 的 license 數 ÷ 有效 license 數 | 買了不用的人最容易退款、最不會推薦 | 【建議】低於 60% 就寄 onboarding 信 |
| **Pro 意圖數** | `/r/pro/*` 回 401 的次數與不重複區塊 | 沒買但想裝 = 最接近購買的人 | 無，看趨勢 |
| 免費安裝（CLI / agent） | 現有 `installs:*` 的 tool 類 | 漏斗頂端 | 每週看前 10 名是否動效佔多數 |

### 3.2 訂單（Orders）
- 訂單數、營收、淨營收、客單價：Polar Metrics，可切日 / 週 / 月與產品。
- 產品組合：Founding / Pro / Team 各佔多少筆與金額。
- **退款率**：30 天內退款筆數 ÷ 同期訂單，附退款原因（若有填）。買斷授權沒有公開的退款率基準【查無一手資料】，先建立自己的基線。
- 國家分布：對應台灣報稅與 Polar 換匯費用估算，可匯出 CSV 給會計師。
- 結帳轉換：`checkouts` → `succeeded_checkouts`、`checkouts_conversion`。

### 3.3 授權使用率（Licenses），Polar 沒有、只有 SunUI 有
每把 license（以 Polar license id 為鍵，**不存 key 本身**）：
- 首次安裝時間、**購買到首次安裝的天數**（time to first install）。
- 累計 Pro 安裝次數、裝過哪些 block、最後一次使用日。
- 每日不重複 IP 數（用 HyperLogLog 估算，見 4.2），超過門檻標紅：疑似分享。
- Team 方案：Polar activations 數 ÷ 5 席，即席位使用率。
- **沉睡名單**：買超過 3 天仍 0 安裝的 license，一鍵複製 email 寄教學。

### 3.4 Pro 區塊表現
- 每個 Pro block：授權安裝次數、401 次數、**401 ÷ 型錄頁瀏覽**（若之後有流量資料）。
- 401 多但購買少的 block 代表「有興趣但價格或說明擋住」；安裝多的 block 是行銷素材首選。

### 3.5 免費安裝
- 沿用現有 `installStats`，加上依 `registry.json` 的 `meta.series` 分組，直接回答商業模式分析每週要看的問題：「前 10 名是不是動效佔多數」。
- 來源比例：browser（型錄預覽）對 tool（CLI / agent）。

### 3.6 AI 通路（MCP）
- 每個工具每日呼叫數。
- `search_blocks` 的查詢詞排行（正規化、截斷 40 字、不存 IP）。
- **零結果查詢**：agent 找不到東西的詞，是最準的新 Pro scene 需求清單。
- `plan_install` 中含 Pro block 的比例：agent 推薦 Pro 的頻率。

### 3.7 漏斗
`免費安裝 / MCP 呼叫` → `pricing 頁瀏覽` → `點結帳` → `Polar checkout 建立` → `付款成功` → `首次 Pro 安裝`

前兩步自己計數，中間兩步來自 Polar Metrics，最後一步來自授權使用紀錄。這條鏈只有 admin 能串起來。

### 3.8 系統健康
- Polar validate 回 503 的次數（授權伺服器不穩會直接擋住付費客戶）。
- 429（限流）與 403（分享）次數。
- Webhook 最後成功時間與失敗次數。
- Redis 本月 commands 用量 ÷ 500K。

## 4. 資料收集設計

所有計數沿用 `lib/installs.ts` 的作法：Upstash REST pipeline、無套件依賴、edge 可跑、`event.waitUntil` 非同步寫入、失敗不影響使用者、日期用 UTC（與現有資料一致）、預設保留 180 天。

### 4.1 Redis key 設計【建議】

| Key | 型別 | 內容 | 寫入點 |
|---|---|---|---|
| `installs:{day}`、`installs:{day}:kind` | hash | 已存在 | middleware |
| `pro:{day}` | hash | block → 授權安裝次數 | Pro route 成功時 |
| `pro401:{day}` | hash | block → 401 次數 | Pro route 無 key 時 |
| `prodeny:{day}` | hash | `401` / `403` / `429` / `503` → 次數 | Pro route 失敗時 |
| `lic:{licenseId}` | hash | `first`、`last`、`count` | Pro route 成功時（`HSETNX first`） |
| `lic:{licenseId}:blocks` | set | 裝過的 block | 同上 |
| `lic:{licenseId}:ip:{day}` | HyperLogLog | 加鹽雜湊後的 IP | 同上，TTL 2 天 |
| `revoked` | set | 已撤銷的 license id | webhook |
| `mcp:{day}` | hash | 工具名 → 次數 | MCP route |
| `mcpq:{day}`、`mcpmiss:{day}` | sorted set | 查詢詞 → 次數；零結果詞 → 次數 | search_blocks / search_icons |
| `funnel:{day}` | hash | `pricing_view`、`checkout_click:{plan}` | pricing 頁、結帳轉址 route |
| `webhook:last` | hash | 事件類型 → 最後成功時間 | webhook |

### 4.2 Pro route 改動
1. 成功回傳前寫 `pro:{day}`、`lic:*`。
2. 無 key 時寫 `pro401:{day}`；授權失敗時寫 `prodeny:{day}`。
3. **把 `license.ts` 的 IP 計數與限流搬到 Redis**：用 `PFADD lic:{id}:ip:{day} <hash>` 與 `PFCOUNT`，多 instance 下才準。IP 只以「每日輪替鹽值 + SHA-256」存在 HLL 裡，無法還原，也不存原文。
4. 驗證前先查 `SISMEMBER revoked <licenseId>`，讓退款後的撤銷在所有 instance 立刻生效。

### 4.3 Polar webhook（新增 `app/api/polar/webhook/route.ts`）
- 驗證 Standard Webhooks 簽章（`POLAR_WEBHOOK_SECRET`），失敗回 403。
- 訂閱 `order.paid`、`order.refunded`、`refund.created`、`benefit_grant.created`、`benefit_grant.revoked`。
- `benefit_grant.revoked`：把 license id 加進 `revoked`。
- `order.paid`：用 Resend 寄一封「新訂單」通知給自己（可選），寫 `webhook:last`。
- 訂單本身**不複製一份到 Redis**，Polar 是唯一的資料來源，admin 讀取時打 API。

### 4.4 結帳點擊計數（不放追蹤 JS）
- 新增 `app/go/checkout/[plan]/route.ts`：計數 `funnel:{day}` 的 `checkout_click:{plan}` 後，302 轉到 `checkoutUrls[plan]`。pricing 頁按鈕改指向這個 route。
- pricing 頁瀏覽：在 page 的 server component 計數（排除 bot user agent），或在 middleware 對 `/pricing` 計數。

### 4.5 MCP route
在每個 `registerTool` handler 開頭呼叫 `recordMcp(tool, query?, resultCount?)`。查詢詞先轉小寫、去頭尾空白、截斷 40 字；結果數為 0 時寫進 `mcpmiss`。

### 4.6 用量估算
每個事件約 2 到 6 個 Redis commands。以 4 個平均計，免費額度 500K / 月約可容納每天 4,000 個事件。平常足夠，但 **Product Hunt 當天（2027-01-12）很可能超過**。【建議】PH 前一週在 Upstash 加付款方式改隨用隨付，10 萬 commands 只要 US$0.20，成本可忽略，但能避免當天計數全部失效。

## 5. Admin 介面

### 5.1 位置與存取
- 放在同一個 Next.js app：`app/(admin)/admin/...`，`dynamic = "force-dynamic"`，Node runtime。
- **未登入一律回 404**（不是 401，避免暴露有後台），`robots.ts` 加 `Disallow: /admin`，頁面加 `noindex`。
- 登入【建議】：不加套件。`/admin/login` 表單輸入 `SUNUI_ADMIN_TOKEN`，伺服器以 Web Crypto 做 HMAC 簽名的 HttpOnly、Secure、SameSite=Strict cookie（7 天），middleware 驗簽；登入嘗試以 IP 限流（Redis）。之後若有協作者再換成 GitHub OAuth 白名單。
- 只讀：第一階段不做任何寫入 Polar 的動作（退款、撤銷都回 Polar 後台做），降低後台被盜的損害。

### 5.2 頁面
| 頁面 | 內容 | 資料來源 |
|---|---|---|
| 總覽 `/admin` | 3.1 的五個數字 + 7 / 30 天趨勢迷你圖 + 距 Founding 截止天數 + 門檻進度條 | Polar Metrics + Redis |
| 訂單 `/admin/orders` | 訂單表（email 遮罩，可展開）、產品組合、退款率、國家分布、CSV 匯出、連到 Polar 訂單頁 | Polar Orders / Metrics |
| 授權 `/admin/licenses` | 每把 license 的首次 / 最後使用、安裝數、block 清單、IP 警示、Team 席位；沉睡名單 | Polar License Keys + Redis `lic:*` |
| Pro 區塊 `/admin/pro` | 每個 block 的安裝數、401 數、比值排序 | Redis |
| 免費 `/admin/installs` | 排行、系列分組、來源比例、每日趨勢 | Redis（現有） |
| AI 通路 `/admin/ai` | 工具呼叫趨勢、熱門查詢、零結果查詢 | Redis |
| 漏斗 `/admin/funnel` | 3.7 的六步驟，可切 7 / 30 / 90 天 | Redis + Polar |
| 系統 `/admin/health` | 503 / 429 / 403、webhook 最後成功、Redis 用量 | Redis + Upstash |

### 5.3 視覺
- 吃自己的狗糧：趨勢圖用免費的 `tiny-chart`、狀態用 `status-dot`、空資料用 `empty-state`，排版遵守 `DESIGN.md` 的紙感。
- **不能 import Pro 的 `count-chart`**：Pro 目錄在公開 repo 裡是 gitignored，admin 程式碼在公開 repo，引用 Pro 會讓公開 repo 建置失敗，也違反「Pro 原始碼不進公開 repo」的規則。
- 後台不屬於 site chrome 動效規範的範圍，保持安靜：數字不跑動畫，只有載入淡入。
- 文案只給作者看，不需要四語；仍放在 admin 自己的檔案，不混進 `lib/messages.ts`。

### 5.4 快取
- Polar Metrics 與 Orders：`fetch` 加 `next: { revalidate: 300 }`（5 分鐘），頁面提供「立即刷新」按鈕。
- License Keys 列表（最多數百把，每頁 100）：同樣 5 分鐘。
- Redis 計數：每次即時讀，一頁大約 1 到 3 個 pipeline 請求。

## 6. 隱私與安全

- 不存 IP 原文、不存 user agent 原文、不存 license key 本身（只存 Polar license id）。
- MCP 查詢詞只存截斷後文字與次數，沒有任何使用者識別。
- 客戶 email 只在 admin 頁面從 Polar 即時讀取，不落地到 Redis。
- 新增環境變數：`SUNUI_ADMIN_TOKEN`、`SUNUI_ADMIN_COOKIE_SECRET`、`POLAR_ACCESS_TOKEN`（只給 `metrics:read`、`orders:read`、`license_keys:read`、`customers:read`）、`POLAR_WEBHOOK_SECRET`。都設為 Vercel Secret、只給 Production。
- 隱私頁補一句：「為了服務品質，我們以匿名方式記錄 registry 與 MCP 的使用次數。」

## 8. 刻意不做的事

- **不自建訂單資料庫**：Polar 是 Merchant of Record，訂單與稅務以它為準，自己複製一份只會產生對帳問題。
- **不做後台寫入動作**（退款、撤銷、改價）：回 Polar 後台處理。
- **第一階段不放前端追蹤 JS**：省掉 cookie 橫幅與隱私審查，伺服器端計數已涵蓋漏斗關鍵步驟。
- **不做即時推播大螢幕**：一個人經營，每天看一次就夠。
- **不碰免費型錄凍結**：admin 不是 block，不違反 2026-11-06 的凍結決定。

# 為什麼要上 shadcn 官方索引：深度分析

日期：2026-11-22。起因：使用者問「為什麼一定要？」。前兩份報告（〈為什麼建立在shadcn上〉、〈shadcn官方索引提交準備〉）把提交索引列為第一優先，這份回頭檢查這個判斷，並更正前面說得太滿的地方。

## 1. 結論

**不是一定要。** SunUI 不上索引也能正常運作，現在任何人用完整網址就能安裝。

但它仍然值得做，理由是**成本極低、風險很小、對 PH 上線有幫助**。真正要先決定的不是「要不要」，而是**網域要不要換**：索引登記的是網址，網址公開後再換，要重新送 PR，舊網址也得永遠轉址。

建議：先決定網域，確定不換就在 12 月中前送出，讓健康分數在 2027-01-12 PH 上線前累積好。

## 2. 更正：前面說得太滿的地方

我在前面寫過「`shadcn search` 與 agent 都會查這份索引」「AI 搜尋元件時查的也是這份名單」。查了 shadcn 官方文件（2026-11-22）後，這兩句要更正：

| 我說的 | 實際情況 | 來源 |
|---|---|---|
| AI 會從索引裡找到 SunUI | shadcn MCP 只搜尋使用者 `components.json` 裡**已經設定**的 registry | [MCP 文件](https://ui.shadcn.com/docs/mcp)：「Registries are configured in your project's components.json」 |
| `shadcn search` 會搜整份索引 | `search` 要指定 registry，例如 `search @shadcn -q "button"` | [CLI 文件](https://ui.shadcn.com/docs/cli) |
| 不在索引就等於少一大塊通路 | 說太重了。索引的作用是「免設定」，不是「自動被推薦」 | [命名空間文件](https://ui.shadcn.com/docs/registry/namespace)：「No automatic registry discovery」 |

## 3. 上索引實際改變什麼

| 改變 | 現在（不在索引） | 上索引後 |
|---|---|---|
| **用命名空間安裝** | 要先在 `components.json` 加一段設定，否則 `npx shadcn add @sunui/xxx` 會失敗 | 直接就能裝，CLI 會自動把 SunUI 寫進使用者的設定 |
| **AI agent 安裝** | agent 要知道完整網址，或先幫使用者加設定 | agent 只要寫出 `@sunui/countdown-banner` 就能裝成功。從 `llms.txt`、MCP、文件學到這個寫法的 agent，不會在第一步卡住 |
| **曝光** | 只有自己的網站、README | 列在 shadcn 官網的 [Registry Directory](https://ui.shadcn.com/docs/directory) 頁面，跟 593 個 registry 並列 |
| **可信度** | 無 | 公開的健康狀態與分數（可用性、schema 正確性、可安裝） |
| **排序** | 無 | 健康分數接近時，項目多的排前面。SunUI 免費 114 個，不算少 |

最實際的是前兩項：**少一個設定步驟，安裝失敗率就低一截**。不論是人還是 agent，第一次 `@sunui/xxx` 失敗，多半就不會再試。

## 4. 成本與風險

| 項目 | 程度 | 說明 |
|---|---|---|
| 工作量 | 低 | 條件已全部驗證過，送出約 30 分鐘；審核時間不確定 |
| **網址要長期固定** | **高** | 索引登記 `https://sunui.synvize.com/r/{name}.json`。如果之後改用自己的網域（例如 sunui.dev），要再送一次 PR，舊網址也要永遠轉址，否則已經裝過的人與健康檢查都會壞。11-04 的規劃寫過「registry URL 一旦公開就不宜換」 |
| 公開的健康紀錄 | 中 | 網站掛掉或區塊壞掉，會公開顯示「Degraded」或「Unavailable」。目前 `/r/` 是靜態產生，風險低 |
| 只收免費區塊 | 低 | Pro 仍要使用者自己設定授權。這是預期中的：索引帶人進來，Pro 在網站上轉換 |
| 原始碼被看到 | 無 | 免費區塊本來就是公開的 MIT |

## 5. 不上索引的替代做法

- **繼續用完整網址**：文件、README 寫 `npx shadcn add https://sunui.synvize.com/r/xxx.json`。可行，但網址長，agent 也比較容易寫錯。
- **GitHub 位址 `owner/repo/item`**：shadcn 支援不用登記的 GitHub 位址，但要求 registry 在 repo 根目錄。SunUI 的 registry 在 `apps/web/`，不符合。
- **教使用者先加設定**：安裝文件已經寫了，但每多一步就少一批人。

這些都能用，只是都比「上索引」多一步。

## 6. 時機

| 時間點 | 為什麼 |
|---|---|
| 先決定網域 | 第 4 節的唯一高風險項目。`apps/web/README.md` 仍寫「正式網域：待買網域」，11-07 的報告則把 `sunui.synvize.com` 記為完成，兩邊不一致 |
| 12 月中前送出 | 新 registry 有 24 小時觀察期，分數會隨檢查次數慢慢貼近實際表現。提早一個月，PH 那天就有穩定的分數 |
| 不要等到 PH 當天 | PR 審核時間不確定，PH 流量進來時 `@sunui/xxx` 若還裝不起來，就浪費了最大的一波曝光 |

## 7. 判斷

上索引不是必要條件，是**投入最少、能降低安裝失敗的一步**。前面把它講成「少一半通路」是錯的，實際好處是「免設定」與「多一個曝光位置」，加上一個公開的可信度分數。

要做，但先把網域定下來。網域定了，就沒有理由不送。

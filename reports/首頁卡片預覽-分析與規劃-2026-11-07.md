# 首頁卡片預覽：問題分析與完整規劃（2026-11-07）

## 一句話結論

首頁卡片壞掉不是 CSS 小問題，是**卡片沒有自己的內容**：145 張卡裡有 98 張直接拿「展開面板用的完整 demo」塞進 357×286 的格子，再由 `FitStage` 無下限地等比縮小。完整 demo 裡常常有好幾個實例、說明文字、控制列，縮到最後就是一條看不清的細長縮圖。修法是讓**每張卡只放一個主角**，並加上自動守門，讓壞卡進不了首頁。

---

## 1. 量測方法與數據

在 dev server 上，以首頁桌機三欄的實際卡片尺寸（`max-w-6xl` 扣邊距，約 **357×286**）載入每一個 `/preview/<name>/card`，等 3.5 秒後讀 `FitStage` 算出的 `scale`、block 實際寬高。

| 縮放比例 | 數量 | 意義 |
|---|---|---|
| < 0.25 | **10** | 完全看不出是什麼，一條細縫 |
| 0.25 ~ 0.5 | **15** | 字看不清，像壓扁的截圖 |
| 0.5 ~ 0.7 | **17** | 勉強可辨，寬版元件被擠成手機版 |
| ≥ 0.7 | 103 | 大致正常（仍有部分是多實例或被橫向裁切） |

最嚴重的十張（scale／內容實際高度）：

| block | scale | 內容高度 | 問題 |
|---|---|---|---|
| photo-looks | 0.032 | 7672px | 24 種濾鏡疊成一長條 |
| camera-moves | 0.042 | 5899px | 22 種運鏡 |
| scene-transitions | 0.048 | 5095px | 全部轉場一路往下排 |
| motion-principles | 0.055 | 4438px | 18 個原則 |
| gradient-backdrop | 0.084 | 2936px | 多種漸層背景 |
| tiny-chart | 0.127 | 1933px | 多個小圖表場景 |
| type-motion | 0.135 | 1818px | 7 種字體動態 |
| raster-image | 0.155 | 1583px | 5 種點陣化樣式 |
| jobs-tray | 0.197 | 1249px | 佇列、格子、面板、工作匣整套控制台 |
| point-cloud | 0.212 | 1161px | 球體、文字、波浪三種點雲 |

另外兩類目視才看得出的問題：

- **橫向被裁掉**：testimonial-marquee、hero-billboard-carousel、store-help-widget 右側直接被卡片切掉（跑馬燈本來就無限寬，`FitStage` 只量 root 的 `offsetWidth`）。
- **寬版元件被當手機排**：store-header、cookie-consent、dialog-sheet、toc-scrollspy、back-to-top、browser-frame 都以 360px 手機寬排版，再縮到 0.5 左右，看起來像「縮小的手機截圖」，不是它在桌機上的樣子。book-3d 是 560px 固定寬，被縮到 0.55。

Pro 場景大多正常（多數有 `card.tsx`），需要處理的是 store-help-widget 0.41、receipt-printer 0.56、peel-sticker-coupon 0.57、fold-invite-card 0.61、price-history 0.71。

完整原始數據：本報告附錄。

## 2. 根因

### R1：15 個動效庫沒有 `variants.tsx`，整本字典塞進一張卡

拆卡機制早就有了（`variants.tsx` → `generate-previews.mjs` → 首頁一種樣式一張卡，收合時跑 `featured`），但只有最早的 13 個效果庫有用。後來加的 15 個動效庫全部沒有：

`photo-looks`、`camera-moves`、`scene-transitions`、`motion-principles`、`type-motion`、`gradient-backdrop`、`raster-image`、`point-cloud`、`brush-reveal`、`spring-rig`、`dial-scrubber`、`depth-hero`、`plush-portrait`、`orbit-gallery`、`ribbon-carousel`、`infinite-canvas`（另 `hover-motion` 連 `meta.series` 都沒標）。

這就是你說的「只顯示一個元件，結果裡面有好幾個」。

### R2：98 個 block 沒有 `card.tsx`，卡片直接用完整 demo

`BlockPreview` 的邏輯是「有 `card.tsx` 用 `card.tsx`，沒有就用 `demo.tsx`」。但 `demo.tsx` 是寫給展開面板和區塊頁的，目的是**展示全部能力**：多個實例、狀態切換、說明、重播鈕。卡片的目的是**一眼認出它是什麼**。兩個目的不同，卻共用同一份內容。

免費 104 個只有 47 個有 `card.tsx`；scale < 0.7 的非動效 block 幾乎全在沒有 `card.tsx` 的那一半。

### R3：卡片只有一種尺寸，橫幅型元件放不進 5:4 小格

`MIN_LAYOUT_WIDTH = 360` 是為了「別把流動寬度的 demo 擠扁」，對卡片型元件是對的。但 header、cookie banner、hero carousel、跑馬燈、側欄這類「本來就是整條橫幅」的元件，用 360px 排出來是**另一個樣子**（手機版），再縮小，使用者看到的不是它真正的設計。

### R4：`FitStage` 縮放沒有下限

`fit < 1` 就照比例縮，縮到 0.032 也照放。沒有「縮太小就換策略」的分支（例如裁切頂部、或顯示主角就好）。

### R5：沒有守門

`generate-previews.mjs` 只產生 import 對照表，不檢查卡片好不好看。新增 block 時，作者在區塊頁看 demo 是對的，不會發現首頁那張卡壞了。15 個動效庫就是這樣一路累積上來的。

## 3. 外部參考

- **shadcn/ui Blocks**：一個 block 一個預覽區，預覽與程式碼分頁，另有「在新分頁開啟」的獨立路由，並另外準備亮暗兩張靜態截圖。重點是**一個預覽只放一個 block**。
- **Aceternity UI**：元件索引是縮圖卡片格，一張卡一個元件；只有「整組」（例如 Hero Sections 27+ blocks）才用一張集合卡並**標出數量**，點進去才看到全部。
- **Drupal ui_patterns_library_plus 的討論**：卡片預覽以「固定虛擬視窗寬度排版，再用 `transform: scale(卡寬/視窗寬)` 縮進卡片」，與我們 `FitStage` 一樣；他們也把「按元件設定虛擬視窗寬度」當成必要選項，這正是 R3 缺的東西。
- 截圖型縮圖的已知缺點：靜態、會和實際元件不同步。我們的 live iframe 是優勢，應保留，只是要給它對的內容。

結論：業界共識是**卡片 = 一個主角**，集合用「代表 + 數量標籤」，橫幅型元件依自己的視窗寬度排版。

## 4. 設計原則（之後所有卡片都照這個）

1. **一張卡一個主角**。卡片內容由 `card.tsx` 或 `variants.tsx` 決定，`demo.tsx` 只給面板與區塊頁。
2. **集合要拆或要標**。動效庫一律走 `variants.tsx`：收合時跑 `featured` 並標「N 種樣式」，Motion 系列或搜尋時展開成一種一張。
3. **元件決定自己的排版寬度**。卡片型（按鈕、票券、卡片）用 360；橫幅型（header、banner、hero、跑馬燈）用桌機寬排版。
4. **縮放有下限**。卡片 scale 不得低於 **0.6**；低於就代表內容選錯了，不是縮放要更努力。
5. **有自動守門**。新 block 或改 demo 時，卡片不合格要在 typecheck 或 CI 前就被擋下。

## 5. 執行計畫

### P0：止血（最多人看到的壞卡），約 1.5 天

**P0-1 給 15 個動效庫補 `variants.tsx`**（基礎建設已存在，每個約 15~30 分鐘）

- 多數 block 檔裡已有樣式陣列（例如 `photoLooks`），`variants.tsx` 只要 `export const variants = photoLooks`、挑一個會自己動的當 `featured`、寫一個只渲染單一樣式的 default export。
- `hover-motion` 補上 `meta.series: "motion"`。
- 不算新增免費 block，**不違反 2026-11-06 的免費型錄凍結**。

**P0-2 卡片守門腳本** `scripts/check-cards.mjs`

- 用 Playwright（或 dev 模式下的內部頁 `/preview/_audit`）在 357×286 與 343×274（手機一欄）兩種尺寸載入每張卡（含 `/v/<featured>`），讀 `FitStage` 的 scale 與 `scrollWidth`。
- 規則：`scale < 0.6` 或內容橫向超出卡片 → 失敗，列出 block 名稱與數值。
- 先以「報告模式」上線（只列出不擋），P1 做完後改成 CI 必過。
- 讓 `FitStage` 在 `data-fit-scale` 屬性上寫出 scale，腳本不用再 regex 解析 transform。

### P1：補卡片內容，約 2~3 天

**P1-1 為 scale < 0.6 的非動效 block 寫 `card.tsx`**，每個只放一個主角、預設狀態要「自己會動或一眼看得出」：

| 類型 | block | `card.tsx` 放什麼 |
|---|---|---|
| 多實例 | tiny-chart、sliding-tabs、stamp、product-media、spine-shelf、scroll-timeline | 只留最具代表性的一個 |
| 整套介面 | jobs-tray、app-shell、store-help-widget、content-gate | 只留主元件（例如工作匣本體），其他版面拿掉 |
| 長內容 | scroll-tilt-stage、hotspots、toc-scrollspy、back-to-top、lightbox、step-demo | 截短內容，保留觸發點 |
| Pro | receipt-printer、peel-sticker-coupon、fold-invite-card、price-history | 同上；Pro 的 `card.tsx` 留在 Pro repo |

**P1-2 `meta.card` 設定**（registry.json 的 meta，與 `usage` 同層）

```jsonc
"card": {
  "layout": 1024,     // 排版寬度，預設 360；橫幅型設 1024 或 1280
  "span": 2,          // 首頁網格佔幾欄，預設 1
  "crop": "top"       // 放不下時裁切對齊方式，預設不裁（等比縮）
}
```

- `FitStage` 讀 `layout` 取代固定的 `MIN_LAYOUT_WIDTH`。
- `BlockCard` 讀 `span`：`lg:col-span-2` 並改用 `aspect-[5/2]`（兩欄寬、同一列高度不變，網格不會亂）。
- 適用：store-header、cookie-consent、announcement-strip、hero-billboard-carousel、testimonial-marquee、browser-frame、dialog-sheet、book-3d。
- 跑馬燈類加 `crop: "left"`，讓它在卡片裡正常流動，而不是被量成無限寬。

### P2：機制收尾，約 1 天

- **縮放下限分支**：`fit < 0.6` 且有 `crop` 時，改為 1:1 顯示並依 `crop` 對齊，底部加一條淡出漸層與「展開看完整」提示，取代無限縮小。沒設 `crop` 的保留現行行為，但守門腳本會擋。
- **橫向溢出偵測**：`FitStage` 量寬度時一併看子孫的 `scrollWidth`，或對 `crop: left` 的 block 不計入。
- **文件**：`apps/web/README.md` 新增 block 步驟加上「寫 `card.tsx`（或 `variants.tsx`）並跑 `check-cards`」；`DESIGN.md` 系列文件加一節「卡片預覽」，`lib/agent/guidelines.ts` 同步英文版。
- 守門腳本改成 CI 必過。

### 驗收標準

- 357×286 與 343×274 兩種尺寸下，所有卡片 scale ≥ 0.6、沒有橫向裁切。
- 收合狀態下，沒有任何一張卡同時顯示兩個以上的同類實例（動效庫以 `featured` 代表並標樣式數）。
- 橫幅型元件在卡片中呈現的是桌機版面。
- 新增 block 若缺卡片內容或不合格，守門腳本會失敗。

## 6. 順序與時程建議

| 順序 | 項目 | 為什麼先做 |
|---|---|---|
| 1 | P0-2 守門腳本（報告模式） | 先有量尺，後面每一步都能驗證，也避免邊修邊壞 |
| 2 | P0-1 動效庫 `variants.tsx` | 最嚴重的 10 張裡 8 張在這裡，改法單純 |
| 3 | P1-1 `card.tsx` | 第二大來源 |
| 4 | P1-2 `meta.card` 與寬卡 | 需要動 `FitStage`、`BlockCard`、registry schema，屬架構變更 |
| 5 | P2 收尾與文件 | 守門改成必過 |

總計約 5 個工作天，在 2027-01-12 Product Hunt 前很充裕；首頁型錄是發表當天流量第一眼看到的東西，值得排在 Pro 新場景之前。

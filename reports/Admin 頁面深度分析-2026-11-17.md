# SunUI Admin 頁面深度分析

> 撰寫日期：2026-11-17。依據：`apps/web/app/(admin)/**`、`lib/admin*.ts`、`lib/orders.ts`、`lib/events.ts`、`lib/google-auth.ts`、兩個 webhook route，以及 `reports/Admin 統計系統規劃-2026-11-13.md`。只讀程式碼，沒有連線 Redis 或實際登入測試。

## 一句話結論

**登入與權限做得紮實，可以放心；真正的風險在「數字」：Polar 上線後，後台很多地方還停在只有 SHOPLINE 的假設，而且累計數字建立在「最近 500 筆訂單」上，訂單一多就會默默算少。** 另外沉睡名單只能看、不能動，跟它自己寫的「寄一封教學信」對不起來。

## 1. 現況盤點

| 頁面 | 檔案 | 做什麼 |
|---|---|---|
| 登入 | `admin/login/*` | email 魔法連結（綁瀏覽器 nonce）+ Google ID token，白名單 `SUNUI_ADMIN_EMAILS` |
| 總覽 | `admin/page.tsx` | 待辦列、6 個 KPI、每日趨勢、購買漏斗、免費安裝排行、授權失敗 |
| 訂單 | `admin/orders/*` | 4 個 KPI、方案組合、訂單明細（最多 500 筆）、SHOPLINE 連線測試、付款通知紀錄 |
| 授權使用 | `admin/licenses/*` | 啟用率、沉睡名單、Pro 區塊意圖 vs 安裝、全部授權 + 重發 |
| 側欄 | `admin/sidebar.tsx`、`(admin)/layout.tsx` | 導覽、資料來源狀態、Founding 倒數；「AI 通路」「系統健康」標規劃中 |

## 2. 安全性：整體良好

做對的地方：

- 未登入一律 `notFound()`，每個 page 與 server action 都各自檢查 `isAdmin()`，沒有只靠 layout 擋。
- session 是 HMAC 簽章 cookie（`httpOnly`、`path=/admin`、`Lax`），不同用途用不同衍生 key；比對用常數時間 `safeEqual`。
- 魔法連結綁定只存在申請者瀏覽器的 nonce，轉寄或被信箱掃描器先點都登不進去；不論 email 在不在白名單回一樣訊息。
- 登入有限流（Redis 跨 instance，失敗退回記憶體）。Google 走 tokeninfo 並檢查 `aud`、`iss`、`email_verified`、`exp`。
- 客戶 email 全面遮罩；授權只存雜湊與末 4 碼；重發有 `confirm()` 且新 key 只顯示一次。
- `robots.ts` 已 disallow `/admin`，metadata 也是 noindex。

需要注意的點（由重到輕）：

1. **`SUNUI_ADMIN_TOKEN` 一把鑰匙扛三件事。** 它同時是 admin session 的 HMAC 根、登入連結的 HMAC 根，也是授權碼加密（`keyEnc`、`seatKeysEnc`，見 `lib/license-key.ts`）的根。要踢掉外流的 session，唯一方法是換 token，但換了之後：完成頁看不到舊訂單的授權碼、訂閱續約解不開原 key（`lib/orders.ts:225` 已註明會變 null）。建議拆成 `SUNUI_ADMIN_TOKEN`（登入用）與 `SUNUI_LICENSE_SECRET`（加密用），舊資料用舊 key 讀、新資料用新 key 寫。
2. **session 沒綁 email，無法單獨撤銷。** cookie 內容只有到期時間，把某人從白名單移除後，他已拿到的 session 仍有效 7 天。現在只有作者一人，影響小；若之後加夥伴，建議把 email 寫進 payload，`verifySession` 時再查一次白名單。
3. **「不透露後台存在」只做到一半。** `/admin` 回 404，但 `/admin/login` 是公開的 200 頁面。若真的在意，可把登入頁搬到不易猜的路徑；若不在意，把 `lib/admin.ts` 的註解改寫，避免誤導。
4. 限流的 IP 取自 `x-forwarded-for` 第一段，在 Vercel 上可信；若未來換平台要重新確認。

## 3. 資料正確性：最該先修

### 3.1 Polar 上線後，後台還是 SHOPLINE 視角（commit 992bb86 之後）

| 位置 | 現況 | 問題 |
|---|---|---|
| `layout.tsx` 側欄來源 | 只列 Redis、SHOPLINE、付款通知（看 `SHOPLINE_SIGN_KEY`） | 沒有 Polar 的設定狀態；Polar 沒設好時側欄仍顯示全綠 |
| `page.tsx` 尚未設定提示 | 只檢查 Redis、SHOPLINE | 同上 |
| `page.tsx` 頁首 | 「金額為新台幣」 | 已經會出現 `NT$… + US$…` |
| 漏斗最後一步 | source 寫「SHOPLINE 通知」 | 也包含 Polar 付款 |
| `orders/page.tsx` 付款通知紀錄 | 標題寫「SHOPLINE 送來的…」 | 實際上 `webhook:log` 兩家混在一起，Polar 那列 `type` 是事件名，SHOPLINE 驗簽失敗那列是空字串 |
| 連線測試 | 只有 SHOPLINE | 沒有 Polar 的連線測試，第一筆美金訂單才會知道設定對不對 |

### 3.2 累計數字被 500 筆上限截斷

`listOrders()` 預設 `ZREVRANGE orders 0 499`，而**每次有人在結帳頁填完 email 就建立一筆訂單**（含放棄付款的 pending）。總覽的「Founding 付費」「累計銷售額」、訂單頁的「有效訂單」「銷售額」「退款率」全部從這 500 筆算。棄單一多，最舊的已付款訂單就掉出視窗，數字只會變小、不會報錯。

- Founding 筆數：`lib/orders.ts` 已經有 `seats:founding` 計數器（退款會扣回），總覽應直接讀它，這也是 50 筆門檻決策的關鍵數字。
- 銷售額：付款與退款時維護 `revenue:twd`、`revenue:usd` 兩個計數器，或另建只放已付款訂單的 sorted set。
- 授權同理，`listLicenses(1000)` 目前離上限很遠，但同一套邏輯。

### 3.3 期間定義不一致

- 安裝、意圖、漏斗前兩步用 Redis 的 **UTC 日 bucket**（含今天未過完的部分）。
- 漏斗後兩步（建立訂單、付款成功）用 **滾動 `days × 24h`**。
- 訂單頁時間顯示為台北時間。

漏斗四步的分母分子來自不同時間窗，短期間（7 天）轉換率會有幾個百分點的雜訊。建議統一用台北時間的日 bucket，或至少在頁首寫清楚。

### 3.4 「付款完成率」把未過期的 pending 算成失敗

訂單頁的完成率 = 非 pending / 全部，剛建立、使用者還在付款頁的訂單也算進分母。量小時影響明顯，可排除建立不到 1 小時的 pending（SHOPLINE 付款頁本來就 60 分鐘失效）。

## 4. 效能

- `(admin)/layout.tsx` 每次換頁都呼叫 `licenseOverview()` 算沉睡數量，授權頁本身又呼叫一次，同一個請求讀兩遍所有授權與使用紀錄（各是一個 1000 筆的 pipeline）。用 React `cache()` 包住 `licenseOverview` 即可去重。
- `sources()` 每次換頁也讀 `webhook:last`。數量不大，可接受。
- 目前量級完全不是問題，等訂單破千、改成計數器後也就自然解決。

## 5. 功能與 UX 缺口

1. **沉睡名單無法行動。** 頁面寫「寄一封安裝教學信」，但 email 被遮罩、沒有寄信按鈕，作者只能去 Redis 或信箱翻。建議每列加「寄教學信」server action（沿用 `lib/mailer.ts`），寄過記錄日期，避免重寄。這是 Founding 期間最直接影響啟用率的動作。
2. **訂單沒有搜尋、篩選、明細。** 客戶來信說「我付了錢沒收到」時，後台無法用 email 或訂單號找人，也不能「重寄授權信」。建議加：依狀態篩選、輸入完整 email 精確查詢（只比對、不列出）、單筆「重寄授權信」。
3. **金額不符、爭議中只有一行紅字。** 沒有連到該筆訂單，也沒寫該去哪家金流後台；表格內這兩種狀態可置頂。
4. **測試訂單混在明細裡。** 統計已排除，但列表照列；多次按「測試 SHOPLINE 連線」後會洗版，可加「隱藏測試」切換。
5. **側欄的「Pro 區塊」「免費安裝」「購買漏斗」是錨點，不是頁面。** 點了跳到總覽中段，跟其他項目的行為不同；短期可接受，長期照規劃拆頁。
6. **規劃文件與實作已分岔。** 11-13 的規劃建議「訂單、營收直接向 Polar Metrics API 拿」，實作改成自建訂單（因為加了 SHOPLINE 與自發授權）。這個方向是對的（兩家金流只能自己合併），但規劃文件該補一段說明，否則下一個讀的人會以為要接 Metrics API。

| P0 | Founding 筆數改讀 `seats:founding`，銷售額改用計數器 | 50 筆門檻是商業決策依據，不能被 500 筆上限截斷 | 小 |

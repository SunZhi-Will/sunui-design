# 幫每個元件準備完整 Prompt，帶到其他平台（手機 UI 等）：深度分析（2026-11-23）

起因：你覺得 SunUI 的元件也可以各自準備一份很完整的 Prompt，讓人拿去用在不同的程式裡，例如手機 UI。

## 一、結論

**值得做，但不是「替 212 個元件各寫一份 Prompt」，而是「一份平台轉接規則 × 元件原始碼」，再挑少數元件做到人工驗證過。**

1. **方向對**。SunUI 現在只服務 React + Tailwind 的人。手機（SwiftUI、Compose、Flutter、React Native）和其他網頁框架（Vue、Svelte）的人看得到、用不到。在 AI 寫程式的時代，「一份精確規格加一份可參考的原始碼」確實能把元件帶過去。
2. **不要手寫 212 份**。每份要寫、要驗、要跟著程式碼更新，維護不起。改成兩層：平台轉接規則（每個平台一份，全站共用）加上元件自己的資料（原始碼、props、設計規則，這些現在就有）。Prompt 由程式組出來。
3. **和 11-22 的決定有衝突，要先講清楚**。那天定的主打是「不是 prompt，是寫好的程式碼，裝了就一樣」。所以這個功能的定位必須是：**React 上給程式碼，其他平台給移植指南**。它是程式碼的延伸，不是改賣 prompt。
4. **Pro 的移植 Prompt 等於 Pro 原始碼的另一種形式**，必須放在授權檢查後面，不能公開。
5. **最值得帶去手機的元件，剛好是 Prompt 最難還原的**（canvas、濾鏡、3D）。而今天另一份報告說的 92 個 C 級普通元件，帶去手機沒有價值，因為原生平台本來就有。
6. **建議先花 1 到 2 天做試作**：3 個元件 × 2 個平台，真的跑出來看。試作結果決定要不要往下做。不要在沒驗證前就對外說「支援手機」。

## 二、現在已經有什麼（已查證）

SunUI 已經有一條給 AI 的管線，這個想法是在它上面加一段，不是從零開始。

| 已有 | 位置 | 內容 |
|---|---|---|
| 「複製給 agent」Prompt | `apps/web/lib/agent/prompt.ts`（47 行） | 安裝指令、何時用、props 介面、該系列的設計規則、驗收三步 |
| Props 自動抽取 | `lib/agent/props.ts` | 從免費元件原始碼抽出 props 介面。Pro 不抽 |
| 設計規則英文版 | `lib/agent/guidelines.ts` | 給 MCP、skill、`llms-full.txt` 共用 |
| MCP 伺服器 | `app/mcp/route.ts` | 6 個工具：找元件、取元件、安裝計畫、設計規則、找圖示、取圖示 |
| Skill | `lib/agent/skill.ts` | 裝進使用者專案的 `.claude/skills/sunui` |
| 使用說明 | `registry.json` 每個元件的 `meta.usage` | `whenToUse`、`watchOut`、`aliases` |

**缺的那一段**：現在的 Prompt 第一句是「用下面的安裝指令，不要手動重寫」。它只對 React + shadcn 專案有用。對 SwiftUI 專案來說，這份 Prompt 沒有任何可以執行的東西。

另外，規格其實已經有一半寫成數字了：三種彈簧（`snappy` 520/34、`gentle` 240/30、`pop` 620/20/0.8）、按下縮到 0.97、四層高度的陰影值、圓角 6/12/16、單次動畫 400ms 以內。這些數字就是跨平台的共同語言。

## 三、「完整的 Prompt」應該長什麼樣

一份能讓 AI 在別的平台重做出同一個元件的 Prompt，需要七段。右欄是資料從哪裡來。

| 段 | 內容 | 來源 | 現況 |
|---|---|---|---|
| 1. 這是什麼 | 一句話、何時用、何時不要用 | `description`、`meta.usage` | 已有 |
| 2. 結構 | 由哪些部分組成，尺寸、間距、圓角、高度層級 | 原始碼 | 要從程式讀 |
| 3. 狀態與轉場 | 有哪些狀態，誰觸發，每段用哪個彈簧、多久 | 原始碼 | 要從程式讀 |
| 4. 對外介面 | props、回呼、受控或非受控 | `props.ts` 抽取 | 免費已有 |
| 5. 設計規則 | 顏色角色、光、手感 | `guidelines.ts` | 已有，但寫法綁 Tailwind |
| 6. 平台轉接 | 彈簧怎麼換算、hover 沒了怎麼辦、觸控目標、震動回饋、安全區、減少動態 | 新寫 | **缺** |
| 7. 驗收 | 做完要對照什麼：預覽影片、逐項檢查 | `public/cards/` 影片、DESIGN 檢查表 | 素材有，沒接上 |

重點：**第 2、3 段不用另外寫成文字，直接附原始碼就好**。原始碼是最精確的規格，而且永遠不會和實作不同步。現在的模型讀一份 250 行的 React 元件再改寫成 SwiftUI，是做得到的。真正缺的只有第 6 段。

### 平台轉接規則的例子（第 6 段）

這一份每個平台只寫一次，所有元件共用。以彈簧為例：

| SunUI | React（現在） | SwiftUI | Flutter | React Native（Reanimated） | Compose |
|---|---|---|---|---|---|
| snappy | stiffness 520, damping 34 | `interpolatingSpring(stiffness: 520, damping: 34)` | `SpringDescription(mass: 1, stiffness: 520, damping: 34)` | `withSpring(v, { stiffness: 520, damping: 34 })` | `spring(dampingRatio ≈ 0.75, stiffness = 520f)` |
| gentle | 240 / 30 | 同上，240 / 30 | 同上 | 同上 | 阻尼比約 0.97，勁度 240 |
| pop | 620 / 20，質量 0.8 | 加 `mass: 0.8` | `mass: 0.8` | `mass: 0.8` | 阻尼比約 0.45，勁度約 775（Compose 沒有質量，換算進勁度） |

【未驗證】上表是我依各平台 API 的參數意義換算的（Compose 阻尼比 = damping ÷ (2 × √(stiffness × mass))），還沒有實機並排比對過手感。這正是試作要確認的事。

其他要寫進轉接規則的對應：

| 網頁上的東西 | 手機上怎麼辦 |
|---|---|
| hover 狀態 | 手機沒有。改成按住狀態，或直接拿掉。靠 hover 才成立的元件不適合移植 |
| 按下縮到 0.97 | 保留，再加一下輕震動（網頁做不到，手機反而更有手感） |
| `layoutId` 共用外框變形 | SwiftUI `matchedGeometryEffect`、Compose 共用元素轉場、Flutter `Hero` |
| 顏色 token（`bg-card`、`--sunui-spot`） | 對應到平台的語意色與 App 的強調色，深淺模式跟系統 |
| 四層陰影加 1px 邊線 | 平台陰影參數不同，要給換算值，不能照抄 CSS |
| 毛玻璃 | iOS 用系統材質；Android 成本高，低階機要有實色回退 |
| `useReducedMotion` | iOS `accessibilityReduceMotion`、Android 動畫縮放設定 |
| `aria-live` | VoiceOver / TalkBack 的公告 |
| 375px 不破版 | 安全區、動態字級、觸控目標至少 44pt |
| canvas 2D 繪圖 | 各平台都有對應的畫布，可移植但要重寫繪圖程式 |
| SVG 濾鏡（紊流、位移） | 沒有直接對應，要改寫成著色器，難度高 |

## 四、哪些元件帶得過去（用程式碼統計）

我用關鍵字掃了主元件檔（不含 demo），算出各種技術用在多少個元件上。這是粗估，一個元件可能同時命中多項。

| 技術 | 免費（114） | Pro（約 98） | 移植難度 |
|---|---|---|---|
| 彈簧、按壓、狀態切換（幾乎全部） | 約 100 | 約 98 | 低：參數直接對應 |
| 拖曳、指標追蹤 | 26 | 28 | 低到中：手機的手勢反而更自然 |
| 共用外框變形（`layoutId`） | 11 | 20 | 中：各平台有對應，但行為有差 |
| 捲動連動 | 40 | 19 | 中：各平台捲動 API 差很多 |
| 遮罩、裁切 | 23 | 21 | 中 |
| 3D 變形（翻轉、透視） | 18 | 10 | 中 |
| hover 相關 | 71 | 81 | 視情況：只是點綴就拿掉，是主體就不能移植 |
| canvas 繪圖 | 10 | 21 | 高：要整段重寫 |
| 毛玻璃 | 8 | 10 | 中：Android 要回退 |
| SVG 濾鏡 | 7 | 7 | 很高 |
| WebGL / 著色器 | 2 | 4 | 很高 |

再疊上今天 `元件為何普通全面深度分析-2026-11-23.md` 的分級，得到這張判斷表：

| 類型 | 例子 | 帶去手機有價值嗎 | Prompt 還原得了嗎 | 結論 |
|---|---|---|---|---|
| C 級通用件（92 個） | 分頁、OTP、骨架屏、定價表、FAQ | 沒有。原生平台本來就有，AI 也隨手做得出 | 可以 | **不做**。做了也沒人要 |
| 網頁專屬 | `store-header`、`back-to-top`、`toc-scrollspy`、`cookie-consent`、`hover-motion` | 沒有。手機沒有這種東西 | 不適用 | **不做**，直接標「僅網頁」 |
| 手感型微互動 | `confirm-button`、`loading-button`、`favorite-button`、`quantity-stepper`、`range-slider` | 有。手機最吃手感 | 高：就是狀態加彈簧加數字 | **最適合，先做這批** |
| 有物件的 A 級，用一般繪圖 | 券、卡包、集點卡、刮刮卡、抽獎輪、訂單島 | 很有。這是 SunUI 真正的賣點 | 中：要附原始碼和影片對照 | **第二批，要逐一驗證** |
| 有物件的 A 級，用 canvas / 濾鏡 / 著色器 | 玻璃方塊、等高線投票、像素場景、液態玻璃 | 最有 | 低：光靠 Prompt 會走樣 | 先不承諾。標「需手動調整」 |

**最尷尬的地方**：最值得移植的那批，是 Prompt 最不可靠的那批。所以不能對所有元件給同樣的保證，要分級標示。

## 五、和既有決定的四個衝突

### 1. 「不賣 prompt」的定位（11-22）

`Scrolltide競品深度分析與完整規劃-2026-11-22.md` 第六節寫明「賣 prompt：不跟。我們的定位反過來打」，而且規劃中的 /why 頁要用「Prompt 庫每次生成不一樣、要再修」當論點。

如果 SunUI 自己也發 Prompt，這個論點會打到自己。解法是把兩件事分開講：

- React 專案：給程式碼，裝了就一樣。這句話不變。
- 其他平台：給**移植指南**。它附的是真的原始碼和真的預覽影片，AI 是照著一個做好的東西改寫，不是憑一段形容詞從空白生成。這是和 Scrolltide 的差別。
- 老實標示：移植結果會因模型而異，只有「已驗證」清單上的我們實際跑過。

命名上建議叫「移植指南」或「帶到其他平台」，不要叫「Prompt 庫」。

### 2. Pro 原始碼不能外流

`AGENTS.md` 規定 Pro 原始碼不能出現在公開頁面、MCP、`llms-full.txt`。skill 裡也寫了「不要從截圖或描述重建 Pro 元件」。

一份夠精確、能讓 AI 重做出 Pro 元件的 Prompt，實質上就是 Pro 原始碼。所以：

- 免費元件的移植 Prompt：公開，順便當搜尋入口（例如有人搜「SwiftUI 優惠券動畫」）。
- Pro 元件的移植 Prompt：只能走 `/r/pro/*` 那條有授權檢查的路，或 MCP 上一個需要金鑰的工具。公開頁面只顯示「Pro 授權含移植指南」。
- 授權條款要補一句：買家可以把 Pro 元件移植到其他平台用在自己和客戶的專案，但不能散布移植後的原始碼。【未驗證】我沒有讀現行授權全文，這一點要你確認。

### 3. 免費型錄凍結（到 2027-01-12）

這不是新增免費元件，嚴格說不違反凍結。但凍結的用意是「時間放在 Pro 場景和上線工作」。所以範圍要壓小，見第七節。

### 4. 今天剛發現的更大問題

今天的盤點說 68% 的元件在型錄上看起來普通，旗艦的檔期整頁最弱。移植 Prompt **不會改善這件事**：普通的元件帶到手機還是普通。如果兩件事搶時間，先修元件本身。

## 六、三種做法比較

| | A. 轉接規則 + 原始碼（自動） | B. 人工驗證的精選清單 | C. 真的出原生程式碼 |
|---|---|---|---|
| 做法 | 每個平台寫一份轉接規則。Prompt = 元件原始碼 + props + 設計規則 + 轉接規則 + 預覽影片連結，由程式組出來 | 在 A 之上，挑 10 到 20 個元件，每個平台實際跑一次，補上該元件的特別注意事項，附移植後的截圖 | 像 libraries.dev 那樣，直接維護 SwiftUI、RN 版本 |
| 涵蓋 | 全部免費元件立刻有；Pro 走授權 | 10 到 20 個 | 少數幾個 |
| 每個元件的成本 | 接近零 | 每個元件每個平台約半天 | 每個元件每個平台數天，之後永久維護 |
| 品質保證 | 沒有，標「未驗證」 | 有，標「已驗證」 | 最高 |
| 會不會過期 | 不會，原始碼改了 Prompt 跟著變 | 特別注意事項可能過期，量少可以管 | 會，兩份程式碼要同步 |
| 前期工作 | 約 2 到 3 天 | A 完成後，每批 3 到 5 天 | 不建議現在做 |

**建議：A 當底，B 做一小批，C 不做。** 不建議另外替每個元件手寫一份純文字規格，因為它會和程式碼不同步，而原始碼本身就是最好的規格。

### 平台順序

| 順序 | 平台 | 理由 |
|---|---|---|
| 1 | Vue、Svelte | 還是網頁，Tailwind 類別和顏色 token 原封不動，只換框架語法。還原度最高，幾乎是機械式改寫 |
| 2 | React Native | 同一種語言，彈簧參數直接對應，會寫 React 的買家最可能順手要這個 |
| 3 | SwiftUI | 手機裡最在意手感的一群人，和「質感」定位最合 |
| 4 | Compose、Flutter | 等前三個有結果再說 |

你提的是手機 UI，但我建議第一個做 Vue / Svelte：它最容易成功，而且同樣把市場擴到 React 以外。

## 七、建議的步驟

### 步驟 0：試作（1 到 2 天，先做這個）

挑 3 個元件、2 個平台，真的把 Prompt 丟給模型、把結果跑起來，和原版並排看。

| 元件 | 為什麼挑它 |
|---|---|
| `confirm-button` | 簡單。兩段式確認、同一顆按鈕變寬變色、提示行。測轉接規則的基本功 |
| `range-slider` | 中等。拖曳、吸附、數值氣泡。測手勢對應 |
| 一個有物件的 Pro 元件（例如 `scratch-card` 或 `tear-pack-reveal`） | 難。測「最值得移植的那批」到底還原得了多少 |

平台：SwiftUI（本機有模擬器可以直接跑）和 Vue。

要記錄的三件事：第一次生成和原版差多少；修到可接受要來回幾輪；每一輪的修正能不能寫回轉接規則，讓下一個元件不再犯。

**通過標準**：簡單和中等的元件一到兩輪內做到手感一致。如果連 `confirm-button` 都要來回五輪，這個功能就不值得對外推出。

### 步驟 1：做法 A（試作通過才做，約 2 到 3 天）

- `lib/agent/` 加平台轉接規則，每個平台一份。
- `prompt.ts` 加一個組移植 Prompt 的函式，輸入元件和平台。
- `guidelines.ts` 補一份不綁 Tailwind 的設計規則（用數值和角色描述，不用類別名）。
- 元件頁的「複製給 agent」加平台切換。
- MCP 加一個工具取移植 Prompt；Pro 需要金鑰。
- 每個元件標一個移植等級：已驗證、未驗證、需手動調整、僅網頁。這個可以先從第四節的統計自動推一版，再人工修。
- 四種語言的介面文案同步。

### 步驟 2：做法 B 的第一批（上線後，或當上線的話題）

從手感型微互動挑 10 個左右，在 SwiftUI 上逐一驗證，附並排影片。這本身就是很好的上線素材：「同一個元件，網頁和 iPhone 上一樣的手感」。

### 不建議現在做的

- 替全部元件寫純文字規格。
- 對外說「支援手機」而沒有已驗證清單。
- 把移植 Prompt 單獨定價。建議比照 Pro 圖示包：含在 Pro 授權裡，不另外賣。

## 八、風險

| 風險 | 說明 | 對策 |
|---|---|---|
| 結果品質不穩 | 同一份 Prompt，不同模型、不同次生成結果不同 | 分級標示；只對已驗證清單負責 |
| 稀釋「裝了就一樣」 | 主打訊息變模糊 | React 是程式碼、其他平台是移植指南，兩句話分開講 |
| Pro 外流 | Prompt 夠精確就等於原始碼 | 放在授權後面；條款補移植使用範圍 |
| 支援負擔 | 「我照 Prompt 做出來是壞的」 | 文件寫明未驗證項目不提供支援 |
| 搶走上線時間 | 距 Product Hunt 約七週，今天還發現元件普通的問題 | 先只做 1 到 2 天試作，其餘看結果 |
| 平台規則寫錯 | 例如彈簧換算不準，所有元件一起錯 | 試作時實機並排比對，校正後再推到全部 |

## 九、需要你決定的事

1. **要不要先做試作？** 我的建議是要，1 到 2 天，SwiftUI 加 Vue，3 個元件。
2. **定位用哪個說法？** 建議「React 上是程式碼，其他平台是移植指南」，不叫 Prompt 庫。
3. **Pro 的移植指南含在授權裡嗎？** 建議含，不另外賣。
4. **第一個平台**：我建議 Vue / Svelte 加 SwiftUI 各試一個。如果你只想驗證手機，就只做 SwiftUI。

## 十、這份分析的限制

- 技術統計是關鍵字掃描，不是逐檔閱讀，數字是量級，不是精確值。
- 各平台的彈簧換算、API 對應是依我對這些平台的了解寫的，沒有實機驗證。
- 競品（kobra 每個元件附「帶去別處用」的 Prompt、libraries.dev 同時出 React / SwiftUI / RN、Scrolltide 賣 Prompt）的資訊來自 11-07 與 11-22 的舊報告，這次沒有重新查證。
- 「會不會有人為了移植指南付錢」沒有任何數據。Scrolltide 的存在是旁證，但它的銷售數字我們無法驗證。

# 試作結果（2026-11-23 當天完成）

## 一、結論

**通過，而且比我預期的好很多。** 3 個元件 × 2 個平台，6 份移植全部在**第一輪**就能編譯、能跑、行為正確，沒有任何一份需要來回修。包含我原本預估「還原度低」的 canvas 刮刮卡。

| 元件 | Vue | SwiftUI（iPhone 17 Pro 模擬器） |
|---|---|---|
| `confirm-button`（簡單） | 第一輪通過 | 第一輪通過 |
| `range-slider`（中等，拖曳） | 第一輪通過 | 第一輪通過 |
| `scratch-card`（Pro，canvas） | 第一輪通過 | 第一輪通過 |

原本定的通過標準是「簡單和中等的元件一到兩輪內做到」。實際是零輪修正。所以第一部分第四節那句「canvas 類光靠 Prompt 會走樣」要修正：**至少 2D 畫布這一類帶得過去**。SVG 濾鏡和著色器這次沒有測，仍然未知。

並排畫面：`reports/assets/移植試作-2026-11-23/results/並排比較.html`

## 二、怎麼做的

1. 寫了三份轉接規則：通用規則（`adapters/core.md`）、SwiftUI、Vue。
2. 用一支小程式把「通用規則 + 平台規則 + 元件說明 + 原始碼 + 相依元件原始碼 + demo 原始碼」組成 Prompt，每份約 19 到 35 KB。
3. 每份 Prompt 交給一個**全新的 agent**。它看不到這個專案，也看不到我的分析，只有那份 Prompt。這是在模擬買家自己的 AI。
4. agent 只能寫檔和做型別檢查，不能跑起來看。跑起來驗證是我做的。
5. 每個 agent 花 1.5 到 3.7 分鐘、約 8 到 10 萬 token。

## 三、驗證到什麼程度

**原版對 Vue**：用無頭 Chrome 對兩邊跑同一支操作腳本，逐格取樣。

| 項目 | 原版 | Vue |
|---|---|---|
| 確認按鈕變寬的彈簧：起點、最高點、落定 | 63.4 → 105.4 → 104.2 px | 63.8 → 107.2 → 106.0 px |
| 彈簧過衝量 | 1.2 px | 1.2 px |
| 待確認逾時 | 2595 ms | 2624 ms |
| Escape 取消、執行中停用、完成訊息、訊息自動清除 | 都有 | 都有 |
| 滑桿拖曳中：把手 1.15 倍、數值氣泡、層級提高 | 有 | 有，數值相同 |
| 滑桿鍵盤（方向鍵、PageUp、End）、表單隱藏欄位 | 有 | 有 |
| 刮刮卡：刮到門檻自動全開、結果文字、畫布移除 | 有 | 有 |
| 主控台錯誤 | 0 | 0 |

寬度差 2 px 是字型不同（原版用網站字型）。

**SwiftUI**：在模擬器上實際點、拖、刮，並錄影抽格。三個元件的每個狀態都出現且正確：待確認變寬變色、逾時、執行中轉圈、完成後變灰加刪除線；滑桿拖曳、點軌道跳到最近把手、步進吸附、商品數跟著變；刮刮卡橫刮直刮都有效，刮過門檻自動全開並出現結果圓片。

**沒有驗證到的**（要老實講）：

- iPhone 上的「手感」我只看了影格，沒有人實際用手指操作。彈簧參數是照搬的，但主觀感受要你自己摸過才算數。
- 只測了淺色模式。深色、減少動態、VoiceOver、動態字級都沒實測，只確認程式碼裡有寫。
- 刮刮卡在「可捲動的長頁面」裡會不會和捲動搶手勢，沒測到（試作頁不夠長）。
- 原版刮刮卡的公開預覽是另一份實作，所以刮刮卡只能比畫面，不能像前兩個那樣比數字。
- 每個組合只生成一次。換一個模型、或再生成一次，結果可能不同。
- 影格裡看到一個小瑕疵：iPhone 版完成訊息的顏色比文字早一格切換。

## 四、移植時 agent 自己做的合理調整

這些不是錯，是平台差異。值得知道，因為它們說明「移植」不等於「一模一樣」：

- **手機沒有失焦**：滑桿的數值氣泡在網頁上點過會留著，iPhone 版放開手指就收起。
- **加了震動回饋**：拖到每一格、進入待確認、成功或失敗各有一下。網頁做不到，這是手機版多出來的手感。
- **觸控範圍放大到 44pt**，但畫面大小不變。
- **拿掉的東西**：hover 樣式、游標樣式、表單隱藏欄位、不受控模式。
- **讀不到像素**：SwiftUI 版刮刮卡改用 64×64 的格子自己記錄刮過哪裡，門檻行為一樣。

## 五、轉接規則的缺口（已寫回）

6 個 agent 一共回報了約 40 條「指南缺了、錯了、不清楚」的地方。重複出現、確定要補的已經寫回三份規則檔：

| 缺口 | 幾個 agent 撞到 | 處理 |
|---|---|---|
| `className` 沒有規則 | 4 | 已補 |
| 「保留四語文案表」寫得太絕對，有的元件根本沒有 | 2 | 改成「原始碼有才保留」 |
| motion-v 的 `useReducedMotion` 回傳的是 ref，直接當布林用會永遠為真 | 3 | 已補。這是最容易靜悄悄出錯的一條 |
| 顏色角色表少了 `secondary-foreground`、`card-foreground` | 1 | 已補進通用規則。`SunUITheme.swift` 還沒補 |
| 按壓回饋：規則說用彈簧，原始碼其實是瞬間 | 2 | 改成「照原始碼」 |
| Tailwind 預設過渡時間沒寫（150ms） | 1 | 已補 |
| 同一個元素上兩種時間（寬度用彈簧、顏色用 150ms） | 1 | 已補 SwiftUI 寫法 |
| 固定高度和動態字級怎麼並存 | 2 | 已補 |
| 讀像素的替代做法沒給格子大小 | 1 | 已補（64×64） |
| 相依元件要搬全部還是只搬用到的 | 2 | 已補（只搬用到的） |

還沒解決的：framer-motion 沒寫 ease 時的預設曲線是什麼，agent 是用猜的。比較好的解法在源頭：元件原始碼裡把 ease 寫明。

**注意：補過的規則沒有重跑驗證。** 因為第一版就全過了，重跑只能證明「沒有變差」，我判斷不值得再花 6 個 agent。

## 六、順便發現的原始碼問題

- `confirm-button`：`armedVariant` 的註解寫「pending 時的樣式」，實際是待確認時套用，執行中已經換回原樣式。註解錯。
- `scratch-card`：註解還留著「朱紅印章」和紙感時期的用語，和現在的設計語言不符。
- `range-slider`、`confirm-button`、`scratch-card` 都有 tween 沒寫 ease，靠函式庫預設值。

這三點我都沒有改，等你決定。

## 七、這個結果改變了什麼

1. **「原始碼就是規格」這個假設成立。** 不需要替每個元件另寫文字規格。轉接規則每個平台 60 行左右就夠用。
2. **做法 A（自動組 Prompt）可以直接做。** 組 Prompt 的程式已經有原型（約 50 行），接進 `lib/agent/prompt.ts` 是小工程。
3. **「已驗證」清單的成本比預估低。** 原本估每個元件每個平台半天。這次 6 個組合連生成帶驗證約 1 小時，主要時間花在第一次架專案和寫驗證腳本，這些可以重複用。
4. **Pro 外流的風險被證實。** Pro 的刮刮卡一次就被完整重做成 Vue 和 SwiftUI。所以 Pro 的移植 Prompt 絕對不能公開。這次的 Pro Prompt、Pro 移植碼都只放在暫存區，沒有進這個公開 repo；repo 裡只有畫面截圖。
5. **原本的保留意見還在。** 普通的元件帶過去還是普通；這個功能不解決型錄看起來普通的問題。

## 八、建議的下一步

1. **你先看並排比較頁，並在模擬器上親手摸一下 iPhone 版**（App 還裝在「SunUI Pilot」模擬器上）。手感對不對，只有你能判斷。
2. 手感過關的話，做第一部分說的步驟 1：把轉接規則和組 Prompt 的程式接進 `lib/agent/`，元件頁加平台切換，MCP 加工具，Pro 走授權。估 2 到 3 天。
3. 再補測兩類還不知道的：SVG 濾鏡或著色器的元件一個、捲動連動的元件一個。這兩類決定「需手動調整」那一級要標多少個。

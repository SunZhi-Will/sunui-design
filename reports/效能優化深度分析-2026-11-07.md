# 效能優化深度分析（apps/web）

日期：2026-11-07
範圍：`apps/web` 型錄網站與預覽 iframe。以本機 production build（`next build` + `next start`）實測，Pro 目錄存在（共 145 個 block、198 種效果樣式）。

## 結論先講

網站本身不慢（本機暖機 TTFB 10 到 45 ms），真正的問題是**整站沒有任何一頁能被快取**，以及**型錄卡片的 iframe 很重**。這兩件事在本機看不出來，到了 Vercel 與 Product Hunt 流量高峰（2027-01-12）會直接變成延遲與帳單。

| 優先 | 問題 | 影響 | 預估改善 |
|---|---|---|---|
| P0 | 根 layout 讀 cookie，整站變成動態，`generateStaticParams` 全部失效 | 每張卡片、每個頁面都是一次 serverless 執行，`Cache-Control: no-store` | 預覽頁約 1,200 個變成 CDN 靜態檔，function 呼叫量降一到兩個數量級 |
| P0 | 型錄每張卡片是一個完整 Next.js 應用的 iframe | 每個 iframe 解析約 556 KB JS，同時存活約 20 個 | 主執行緒與記憶體負擔降 50% 以上 |
| P1 | 首頁 RSC payload 過大 | HTML 770 KB（gzip 88 KB），hydration 慢，手機尤其明顯 | payload 約減半 |
| P1 | block 頁 Shiki 冷啟動 | 冷啟動首次 600 ms | P0 修好後自然消失 |
| P2 | `tsconfig.json` 收錄舊的 `.next-*` 型別目錄 | 舊目錄的型別會讓 `next build` 失敗 | 建置穩定 |

## 進度（2026-11-07 更新）

- **P0-1 第一步已完成**：預覽頁移到 `app/(preview)`，有自己不讀 cookie 的 root layout；網站的 root layout 併入 `app/(site)/layout.tsx`。語言改由 iframe 網址的 `?l=` 帶入（`lib/demo-locale.tsx` 的 `previewUrl`），效果庫面板改走 `/preview/<name>/v/<variant>/sheet`。建置後 999 個預覽頁預先產生（原本 0 個），回應為 `x-nextjs-cache: HIT`、`Cache-Control: s-maxage=31536000`。
- **P0-2 第一步部分完成**：`LivePreview` 預載範圍由 600px 縮為 300px，進入範圍後停留 150 ms 才掛載，快速捲過的卡片不再啟動 iframe。全域同時存活上限、畫面外暫停、靜態縮圖尚未做。
- 尚未做：P0-1 第二步（網站頁語言改走 rewrite，首頁與 block 頁仍是 `no-store`）、P1、P2。

## P0-1：整站動態，靜態產生完全沒生效

### 現象

`app/layout.tsx` 的 `RootLayout` 與 `generateMetadata` 都呼叫 `getLocale()`，它讀 `cookies()` 與 `headers()`。根 layout 一旦讀了 request，底下每條路由都會被 Next 視為動態。

建置表上 `/preview/[slug]/card`、`/blocks/[slug]` 顯示為 ●（SSG），但實際檢查 `prerender-manifest.json`：

- `/preview/*`：**0 個**預先產生（建置時嘗試了約 1,200 頁，全部退回動態）
- `/blocks/*`：145 筆，全是 opengraph 圖片，頁面本身 0 筆
- 回應標頭一律是 `Cache-Control: private, no-cache, no-store, max-age=0, must-revalidate`

### 為什麼嚴重

- 型錄每張卡片載入 `/preview/<name>/card` 或 `/preview/<name>/v/<variant>`。訪客往下捲完整個型錄，至少觸發 145 次 SSR；卡片離開畫面 600 px 會卸載，捲回來再請求一次。
- 粗估：PH 當天 1 萬名訪客、每人平均載入 80 張卡片，就是約 80 萬次 function 呼叫，外加冷啟動延遲。這些頁面內容只跟語言有關（4 種），本來應該是 CDN 上的靜態檔。
- 首頁與 block 頁同理，無法被 CDN 快取。

### 建議做法

預覽頁與網站頁分開處理，先做預覽頁（收益最大、改動最小）：

1. **預覽頁獨立 root layout**：把 `app/preview` 移到自己的 route group（例如 `app/(preview)/preview/...`），給它一個不讀 cookie 的 root layout（自帶 `themeScript`）。網站頁放進 `app/(site)` 的 root layout。兩個 root layout 是 Next 支援的寫法。
2. **語言改由網址帶入**：iframe 網址加 `?l=zh-TW`，`DemoLocaleProvider` 在 client 端讀 `useSearchParams()`（或 `LivePreview` 透過 `postMessage` 傳入）。預覽頁 server 端不再讀 request，就能完全靜態。`<html lang>` 可在 client 端設定，預覽頁不需要 SEO（已是 `noindex`）。
3. `/preview/[slug]/v/[variant]` 目前讀 `searchParams.mode`，同樣會變動態：改成路徑區段（`/v/[variant]/sheet`）或 client 端讀取。

網站頁（第二步）：

- 用 middleware 依 cookie / Accept-Language 把 `/blocks/x` rewrite 到內部的 `/[locale]/blocks/x`，頁面從 `params` 拿語言，就能對 4 種語言各自靜態產生並快取。對外網址不變，SEO 也可順便加上 `hreflang`。
- 改動範圍較大（所有 `getI18n()` 呼叫點），可在 PH 前或後視時間決定。

## P0-2：型錄卡片的 iframe 成本

### 現象

`components/live-preview.tsx` 對每張卡片用 IntersectionObserver（`rootMargin: 600px`）掛載 iframe。每個 iframe 是一個完整的 Next.js 頁面，各自啟動一份 React 與 router。

實測單一卡片 iframe：

| 頁面 | JS 檔數 | 傳輸量 | 解析後大小 |
|---|---|---|---|
| `/preview/add-to-cart-button/card` | 12 | 170 KB | 556 KB |
| `/preview/background-effects/v/aurora` | 12 | 170 KB | 561 KB |
| `/preview/product-gallery/card` | 11 | 169 KB | 555 KB |

傳輸量第二次起會走 HTTP 快取，但**解析與執行每次都要重來**。1440 寬的三欄型錄，畫面加上下 600 px 範圍約有 7 列，也就是約 21 個 iframe 同時存活：約 11 MB JS 要解析執行，21 份 React runtime 常駐記憶體。另外有 26 個免費 block 帶無限循環動畫，它們在畫面外但仍在 600 px 範圍內時照樣在跑。

### 建議做法（由小到大）

1. **縮小預載範圍並限制同時存活數**：`rootMargin` 改為約 `200px`；另外維護一個全域上限（例如桌面 9 個、手機 4 個），超過時卸載離畫面最遠的。
2. **畫面外暫停**：同源 iframe 可以直接控制。離開可視區時通知 iframe 暫停（例如 `document.documentElement.dataset.paused` 搭配 CSS `animation-play-state: paused`，framer-motion 的循環可在 `FitStage` 用 `MotionConfig` 控制），不必卸載重建。
3. **靜態縮圖優先**：建置時用 Playwright 為每張卡片截一張 WebP 縮圖，卡片預設顯示縮圖，滑鼠移入、取得焦點或停在畫面中央超過約 300 ms 才換成即時 iframe。首頁首屏會快很多，也解決手機上的記憶體壓力。這是最大的改善，但需要建置流程配合（Pro 縮圖也要能產生）。

建議 PH 前至少完成 1 和 2；3 視時間。

## P1-1：首頁 RSC payload

### 現象

首頁 HTML 原始 770 KB（gzip 後 88 KB），其中 RSC payload 約 513 KB。來源是 `app/(site)/page.tsx` 傳給 `Catalog` 的 `items`：

- 效果庫一種樣式展開成一筆，198 筆樣式各自重複了 `search` 字串（合計約 125 KB）。
- `meta.usage` 整包傳到 client（`whenToUse` 約 26 KB、`watchOut` 約 33 KB），但型錄只用到 `aliases` 做搜尋。

### 建議做法

- 傳給 `Catalog` 前只保留需要的欄位：`meta` 留 `tier`、`interaction`、`series`；`usage` 只留 `aliases`。
- 效果庫改成「一筆 + `variants: string[]`」，由 client 展開，`search` 不再重複。
- 預估 payload 減少約一半，hydration 時間跟著下降。

## P1-2：Shiki

`components/code-block.tsx` 每次請求都呼叫 `codeToHtml`。實測 block 頁冷啟動首次 600 ms，暖機後約 10 到 20 ms（Shiki 內部有快取）。在 serverless 上每個新實例都要重新載入語法與主題。P0 讓 block 頁可以靜態產生後，這段成本只在建置時發生；在那之前可以先用 `createHighlighter` 只載入 `tsx`、`json`、`bash` 三種語言並在模組層級共用。

## P2：建置衛生

- `apps/web/tsconfig.json` 的 `include` 收錄了 `.next-alt`、`.next-prod`、`.next-protest`、`.next-motion` 的型別目錄。`.next-prod` 是 11 月 5 日的舊產物，裡面的 layout 型別已過期，本次用新的輸出目錄建置時直接在型別檢查失敗。每次用新的 `NEXT_DIST_DIR` 建置，Next 也會自動再加一行進 `tsconfig.json`。建議：清掉不用的 `.next-*` 目錄，`include` 只留 `.next/types/**/*.ts`，多開 dev server 時用 `.next-*` 但不提交它們的 include 變更。
- `components/catalog.tsx` 有 ESLint 警告：`activeNames` 每次 render 都是新陣列，讓兩個 `useMemo` 失效。包一層 `useMemo` 即可，影響小。

## 已確認沒問題的部分

- 網站文案 `lib/messages.ts`（1,778 行、四種語言）只在 server 端使用，沒有進 client bundle。
- 全站共用 JS 107 KB（gzip），首頁 First Load 171 KB，在合理範圍。
- middleware 只匹配 `/r/*`，安裝計數用 `waitUntil` 不阻塞回應。
- `llms-full.txt`、`robots.txt`、`sitemap.xml`、`/r/[name]` 是靜態輸出。
- 字型用 `next/font`，沒有外部字型請求。

## 建議執行順序

1. 預覽頁獨立 root layout + 語言走網址（P0-1 第一步）
2. iframe 預載範圍與同時存活上限、畫面外暫停（P0-2 的 1、2）
3. 首頁 payload 瘦身（P1-1）
4. `tsconfig.json` 與舊建置目錄清理（P2）
5. 網站頁語言改走 rewrite，整站可快取（P0-1 第二步）
6. 靜態縮圖（P0-2 的 3）

## 量測方式

- 建置：`NEXT_DIST_DIR=<新目錄> next build --experimental-build-mode=compile` 再 `--experimental-build-mode=generate`（避開 P2 的舊型別問題），檢查 `prerender-manifest.json`。
- 伺服器：`next start` 後用 `curl -w` 量 TTFB 與回應標頭。
- 瀏覽器：在首頁插入卡片 iframe，讀 iframe 內的 `performance.getEntriesByType("resource")`。
- 尚未量測：真實裝置（中階 Android）上的捲動 FPS 與記憶體，以及 Vercel 上的冷啟動時間。建議修完 P0 後用 Vercel Speed Insights 或 WebPageTest 補量。
